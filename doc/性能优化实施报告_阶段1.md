## 2. P0-1 聚合放大器：合并刷新 + 常驻 worker + 复用连接

### 2.1 问题

`refresh_view` 每次触发 = **1 条新线程 + 1 条新 SQLite 读连接**，且**无合并、无去抖**。

触发点分布在每个 provider 的 `ScanCompleted`、切页 / 切标签 / 切时间范围、`Watch → scan_async`。
项目共 14 个 provider，**一轮全量扫描最多触发 ~14 次全窗聚合**，每次 =
「5 条窗口聚合 + 365 天报告 +（图表页）28 条查询」。

```
ScanCompleted × 14  ──►  refresh_view × 14  ──►  thread::spawn × 14 + open_read × 14
                                          └──►  SQL 次数 × 14
```

### 2.2 改动

**① 引入请求结构 `AggRequest`**（`app.rs:42`）——把主线程状态快照成一份可跨线程的所有权数据：

```rust
struct AggRequest {
    seq: u64,
    time_tab: TimeTab,
    db_path: std::path::PathBuf,
    window: TimeWindow,
    charts: Option<(TimeWindow, ChartApp)>,
    report: Option<TimeWindow>,
}
```

**② 启动常驻 worker**（`app.rs:116-138`）——在 `App::new` 起一次，线程内**只 open 一次连接**：

```rust
let (agg_req_tx, agg_req_rx) = async_channel::bounded::<AggRequest>(1);   // 最新请求胜出
let _agg_worker = std::thread::Builder::new()
    .name("tokenmonitor-aggregate".into())
    .spawn(move || {
        let conn = match sqlite::open_read(&agg_db_path) { /* ... */ };   // ← 复用
        while let Ok(req) = agg_req_rx.recv_blocking() {
            let snapshot = compute_view_snapshot(
                &conn, req.seq, req.time_tab, &req.db_path, req.window, req.charts, req.report,
            );
            let _ = agg_view_tx.try_send(snapshot);                        // bounded(1)
        }
    })
    .expect("spawn aggregate worker");
```

**③ `refresh_view` 只投递请求**（`app.rs:482-519`）——不再 spawn、不再 open：

```rust
let req = AggRequest { seq, time_tab, db_path, window, charts, report };
let _ = self.agg_req_tx.try_send(req);   // 队列已有待处理请求 → 丢弃旧的语义，保留最新
```

**④ `compute_view_snapshot` 改收 `&Connection`** —— 去掉内部 `sqlite::open_read`。

### 2.3 前后对比

| 指标（一轮全量扫描） | 改前 | 改后 |
|----------------------|------|------|
| 聚合计算次数 | ~14 | **1~2** |
| 聚合线程数（峰值） | ~14 | **1**（常驻） |
| SQLite 连接 open 次数 | ~14 | **1**（启动时） |
| 线程创建开销 | 每次 ~100µs 级 | 0 |
| SQL 总条数 | ×14 放大 | ×1~2 |

## 3. P0-2 无背压：双 `bounded(1)` 通道

### 3.1 问题

`app.rs:92` 原为 `let (view_tx, view_rx) = unbounded();`。`ViewSnapshot` 携带
`by_provider` / `by_provider_model` / `by_project` / `by_day` / `charts` / `report(365 天)`，
单份可达几十~上百 KB。生产快于消费时**无界积压**，扫描期尤其明显。

### 3.2 改动

两级「最新值」语义：

| 通道 | 容量 | 语义 |
|------|------|------|
| `agg_req_tx → agg_req_rx` | `bounded(1)` | 请求合并：14 次触发 → 只算最新那次 |
| `view_tx → view_rx` | `bounded(1)` | 快照合并：UI 忙时新快照顶掉旧的，不堆积 |

配合既有的 `view_seq` / `applied_seq` 序号，过期快照在 `apply_snapshot` 侧被判为 stale 直接丢弃。

### 3.3 收益

- 通道内**最多 1 份待处理快照**，内存从「O(触发次数 × 快照大小)」降为 **O(1 × 快照大小)**。
- 扫描期不再出现「快照追赶」造成的 UI 长时间连续重绘。

## 4. P1-4 渲染侧：去掉每帧深拷贝与每帧 HashMap

### 4.1 问题

- `ui/report/section.rs:24`：`let data = app.state.report.data.clone();` —— 每帧**整棵 365 天 Vec 深拷贝**。
- `ui/report/section.rs:195`：`ContributionHeatmap::new(days.to_vec())` —— **再拷一次**。
- `ui/report/heatmap.rs:86`：每帧重建 `HashMap<NaiveDate, SumStats>`（365 次哈希插入 + 365 次哈希查找）。

即：**每次渲染 = 2 × 365 元素深拷贝 + 1 次 HashMap 重建**；而 hover 回调 `cx.notify()` 会导致整页重绘，
鼠标划过热力图时**逐格触发**。

### 4.2 改动

**① 日序列改为 `Arc` 共享**（`app/state.rs:326-331`）：

```rust
pub struct ReportSnapshot {
    /// Shared behind an `Arc` because the snapshot crosses the aggregate
    /// worker thread boundary; cloning it (per render, per page) only bumps a
    /// refcount instead of deep-copying 365 `SumStats` entries.
    pub days: Arc<Vec<(NaiveDate, SumStats)>>,
}
```

> **为什么是 `Arc` 而不是 `Rc`**：快照由聚合 worker 线程产出、经 `view_tx` 进入 UI，必须 `Send`。
> 首版用 `Rc` 直接编译失败（`E0277: Rc<...> cannot be sent between threads safely`），已改为 `Arc`。

**② `section.rs` 改为借用 + `Rc/Arc` 级克隆**（`section.rs:25-42`）：

```rust
let content = match &app.state.report.data {      // ← 借用，不再 clone 整棵
    Some(snap) => {
        let stats = report_stats(&snap.days, today);
        ...
        .child(heatmap_card(
            snap.days.clone(),                     // ← Arc clone，仅 refcount++
            app.state.report.heatmap_bounds, hover, &on_hover, &on_resize, cx,
        ))
    }
    None => empty_hint("加载中…", p.muted_foreground),
};
```

`heatmap_card` 签名由 `&[(NaiveDate, SumStats)]` → `Arc<Vec<(NaiveDate, SumStats)>>`，
内部改调新增的 `ContributionHeatmap::from_arc(days)`。**`to_vec()` 已彻底移除。**

**③ 热力图改用有序归并，去掉 HashMap**（`heatmap.rs:74-98`）：

```rust
/// Align the ascending day series onto `len` grid cells that start at
/// `start` and advance one day per cell, zero-filling days without usage.
///
/// Both sides are ascending, so this is a single O(days + len) merge with
/// no hashing — the grid previously paid a 365-entry `HashMap` build plus
/// 365 hashed lookups on every frame (including every hover).
fn aligned_cells(&self, start: NaiveDate, len: usize) -> Vec<SumStats> {
    let mut out: Vec<SumStats> = Vec::with_capacity(len);
    let mut it = self.days.iter().copied().peekable();
    for i in 0..len {
        let date = start + Duration::days(i as i64);
        while it.peek().is_some_and(|(d, _)| *d < date) { it.next(); }
        match it.peek() {
            Some((d, stats)) if *d == date => { out.push(*stats); it.next(); }
            _ => out.push(SumStats::default()),
        }
    }
    out
}
```

关键点：网格按「周主序 + 周次序」遍历，其展开顺序**恰好是日期升序**，与 `self.days` 同序，
因此可以双指针一次归并，无需哈希。

### 4.3 前后对比

| 项目（每次渲染） | 改前 | 改后 |
|------------------|------|------|
| 365 天 Vec 深拷贝 | 2 次 | **0 次**（Arc refcount++） |
| HashMap 构建 | 365 次插入 | **0 次** |
| 日数据查找 | 365 次哈希查找 | **0 次**（顺序索引） |
| 合计复杂度 | O(2n) 拷贝 + O(n) 哈希 | **O(n) 归并**（无拷贝、无哈希） |

## 5. 兼容性处理（踩坑记录）

### 5.1 `load_report_days` 返回类型回退

`report/data.rs` 的 `load_report_days` 是 **GPUI 与 TUI 共用**的加载器。
首版把返回值改成 `Arc<Vec<..>>` 后，TUI 编译报错：

```
src\tui\app.rs:206:21: error[E0308]: expected `Vec<(NaiveDate, SumStats)>`, found `Arc<Vec<...>>`
src\tui\app.rs:229:27: error[E0308]: (同上)
```

**处置**：`load_report_days` 保持返回 `Vec`，只在 GPUI 侧构造快照处包 `Arc`
（`app/app.rs:619-625`），TUI 完全不受影响：

```rust
fn compute_report_snapshot(conn: &Connection, window: TimeWindow) -> ReportSnapshot {
    let mut snap = ReportSnapshot::default();
    if let Ok(days) = crate::report::data::load_report_days(conn, &window) {
        snap.days = Arc::new(days);      // ← 仅此处包装
    }
    snap
}
```

### 5.2 rustc 1.95.0 元数据编码 ICE

切换 feature 编译 TUI 时偶发 rustc 内部错误（`rmeta::encoder` panic: `no entry found for key`），
属编译器 bug，**与本次改动无关**。规避方式：

```bash
CARGO_INCREMENTAL=0 cargo check --no-default-features --features tui
```

### 5.3 Bash 沙箱路径限制

本环境 `cargo --manifest-path /e/...` 取不到 E: 盘（子进程视角），需先 `cd` 进项目目录再执行：

```bash
cd /e/project/TokenMonitor && cargo check --features ui --offline
```

## 8. 度量建议（上线前实测）

改动前建议在三种场景各测一次基线：**空闲 / 手动全量扫描 / 停留在图表页**。

- **CPU**：任务管理器看扫描期峰值；重点比对「扫描期是否还有周期性尖刺」。
- **内存 RSS**：扫描期峰值应明显回落（无界快照积压已消除）。
- **可临时加计数验收后移除**：`refresh_view` 触发次数、实际聚合执行次数、`view_rx` 通道积压深度、
  单次 `compute_view_snapshot` 的 SQL 条数与耗时。
- **预期**：实际聚合执行次数应≈1~2（而非 14），积压深度恒 ≤1。
