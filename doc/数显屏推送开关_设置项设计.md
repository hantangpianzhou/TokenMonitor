> 结论先行：**应用目前没有推送逻辑，开关缺少控制对象。本文先厘清语义、给出三种候选与推荐方案，待确认后再写代码。**

## 一、现状勘查（代码事实，非推测）

### 1.1 应用侧（Rust）没有数显屏推送代码

| 检查点 | 结果 |
|---|---|
| `src/` 全局搜索 `screen` / `数显` / `serial` / `COM` | 无推送相关实现；`app.rs` 里唯一的 "screen" 是主题注释（`on screen`） |
| 托盘菜单 `platform/windows/tray.rs` | 命令仅 `Floating / Quit / Refresh / Dock`，无屏幕推送项 |
| 悬浮球 `ui/floating.rs` | 无屏幕推送入口 |
| 设置页 `ui/settings/page.rs` | 「通用」页现有 3 项：开机自启、扫描间隔、主题色 |

### 1.2 推送是独立的 Python 程序（与应用松耦合）

```
TokenMonitor.exe ──写──> tokenmonitor.db (SQLite)
                              │
                              │ 每 60s 读库（不依赖应用是否运行）
                              ▼
                      screen_loop.exe ──串口──> 图灵智显 3.5"
                      (doc/prototype-turing-screen/)
```

- `screen_loop.py` 常驻循环：启动推一帧 → 数据指纹变化/时钟兜底/触发文件 → 推帧 → 断链重试；
- 自带 `--trigger` 触发文件机制（`%TEMP%\tm-screen-refresh.trigger`），存在即推一帧并清除；
- **当前无任何开关**：进程一旦启动就一直推，只能靠"结束进程"停止。

### 1.3 应用现有的"设置项"标准模式（可复用）

| 层 | 文件 | 机制 |
|---|---|---|
| 存储 | `settings` 表 | key-value 文本，布尔值存 `"true"`/`"false"` |
| 仓储 | `storage/repository/settings_repo.rs` | `get(key)` / `set(key, value)` |
| 领域 | `collector/mod.rs` | 每项一对 getter/setter（如 `floating_window_visible()` / `set_floating_window_visible()`），内部加 db 锁 |
| 实体 | `app/app.rs` | `TokenMonitorApp` 持有字段或 `AtomicU64`，setter 里持久化 + `cx.notify()` |
| UI | `ui/settings/page.rs` | `SettingItem::render` + `Switch::new(...).checked(...).on_click(...)` |

**结论**：加一个布尔开关本身是低成本的（照抄 `autostart_item` / `floating_window_visible` 即可）。真正的问题是——**开关要控制什么**。

## 二、核心歧义：开关的控制对象

"推送数显屏"开关可以有三种完全不同的语义，工程量与用户体验差别很大。必须先选一个。

| 方案 | 开关控制的对象 | 应用要做什么 | Python 要做什么 | 优 | 劣 |
|---|---|---|---|---|---|
| **A. 应用托管进程** | `screen_loop.exe` 的启停 | 启动/结束子进程，开关反映进程是否存活 | 无（或极小） | 语义直观：开=推，关=停 | 要管理子进程生命周期；退出时需清理；跨平台路径 |
| **B. 共享配置标志** | `settings` 表里一个 key | 只写 key，不碰进程 | 每轮读该 key，关则跳过推送 | 改动最小、最松耦合、跨语言干净 | 关掉开关时进程仍在跑（只是不推）；需 Python 配合改 |
| **C. 手动触发按钮** | 触发文件（一次性推帧） | 点按钮写触发文件 | 无（复用现有 `--trigger`） | 零 Python 改动，立即可用 | 不是"开关"是"按钮"，不控制常驻推送 |

### 推荐：方案 B（共享配置标志）

理由：

```
1. 契合现有架构 —— 工作日志已定调「Rust 与 Python 不集成，靠 SQLite 交接」。
   方案 B 延续这条：开关写 settings 表，screen_loop 读 settings 表，两侧只共享一个 key。
2. 改动最小 —— Rust 侧完全是标准设置项（照抄现成模式）；Python 侧只加一个读 key 的判断。
3. 最稳 —— 应用不管理子进程，就不会有"进程残留/僵尸/退出清理/路径找不到"等问题。
4. 语义可接受 —— 用户视角"关掉就不推了"，进程空转但不再写串口，效果等价。
```

方案 A 作为**后续可选增强**：若将来要求"关掉就彻底不占资源"，再在 B 的基础上叠加进程托管。

## 三、推荐方案 B 的落地设计（待确认后实施）

### 3.1 数据流

```
用户在「设置→通用」拨动"推送数显屏"开关
        │
        ▼
app.set_screen_push(enabled)
        │
        ├─ collector.set_screen_push_enabled(enabled)
        │        └─ settings 表: key="screen.push_enabled" value="true"/"false"
        │
        └─ screen_loop 每轮 load_data 前读同一个 key
                 └─ 若 "false" → 本轮跳过推送（LCD 保留上一帧），等下轮再查
```

### 3.2 代码改动点（精确落点）

| # | 文件 | 改动 |
|---|---|---|
| 1 | `src/collector/mod.rs` | 常量 `SCREEN_PUSH_KEY: &str = "screen.push_enabled"`；加 `screen_push_enabled() -> bool`（默认 **false**：未配置时不推，安全侧）与 `set_screen_push_enabled(bool)`；照抄 `floating_window_visible` 那对 |
| 2 | `src/app/app.rs` | `TokenMonitorApp` 加字段 `pub screen_push_enabled: bool`；构造函数从 collector 读初值；加 `set_screen_push(&mut self, bool, cx)`：写 collector + `cx.notify()` |
| 3 | `src/ui/settings/page.rs` | `general_page` 的 group 加一项 `screen_push_item(&weak)`；仿 `autostart_item` 用 `Switch::new("screen-push-switch")` + `setting_row("推送数显屏", ...)`；keywords `["推送数显屏","数显屏","screen","push"]` |
| 4 | `doc/prototype-turing-screen/screen_loop.py` | 循环内每轮（或每隔 N 轮）读 `tokenmonitor.db` 的 `settings` 表 `screen.push_enabled`；为 `false`/缺失则 `log("推送已关闭，跳过")` 并 `continue`（或 `time.sleep`）；建议加 `--ignore-switch` 保留原行为便于自测 |

### 3.3 默认值与边界

| 项 | 取值 | 理由 |
|---|---|---|
| 默认 | `false`（关闭） | 避免老用户升级后突然开始推串口；显式开启才推 |
| 读取频率 | 每轮读（60s 一次） | 开销可忽略；关闭后最多 60s 生效 |
| 读失败 | 视为 `true`（维持原行为） | 兼容尚未更新的 Python / 无 settings 表的旧库 |
| 与 `--trigger` 关系 | 关闭时手动触发也被拦截 | 语义一致；需要可在 Python 侧让 trigger 绕过开关 |

> 注：读写"忽略开关"的兼容策略需在实施时二选一（默认 false vs 读失败当 true），二者针对的是不同情况，不矛盾——前者管"key 不存在"，后者管"读 key 出错"。

## 四、备选方案 A 要点（暂不实施，供决策参考）

若选 A（应用拉起/结束 `screen_loop.exe`），需额外解决：

| 问题 | 处理 |
|---|---|
| exe 路径 | 相对应用安装目录，或 settings 里配一个路径 |
| 启动 | `Command::new(...).spawn()`，保存子进程句柄/ PID |
| 关闭 | Windows 下 `taskkill /PID` 或 `GenerateConsoleCtrlEvent`；注意子进程可能派生 |
| 退出清理 | 应用退出时结束子进程，避免残留 |
| 状态同步 | 用户手动结束进程时开关要回退（需心跳检测） |
| 权限 | 打包进安装包，或提示用户放置路径 |

这些是 B 方案完全不需要承担的复杂度，故不推荐作为第一步。
